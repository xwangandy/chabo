# 频道广告助手机器人产品落地深度研究报告

## 频道数据采集能力边界

为了把“能做的日报/计费/归因”做成可落地的产品，需要先把数据能力分成三层（并严格标注边界）：

- **Bot API（HTTP）**：交互、权限管理、接收频道新帖/编辑事件、取频道基础信息、取成员数等。更新在服务器端最多保留 24 小时，机器人必须持续消费更新，否则会丢事件。citeturn25view0  
- **MTProto（bot 身份，不是 user session）**：用 MTProto 作为 bot 登录后，可获取 MTProto `message` 结构体里的 **views / forwards / reactions / replies** 等字段，从而补齐 Bot API 文档中缺失的“浏览/转发/互动计数”类指标。citeturn26view0turn15search3  
- **MTProto（user session）**：能调用 `stats.getBroadcastStats` / `stats.getMessageStats` 等“官方统计图表/增长来源/图形化指标”，但这两类方法 **官方明确标注 Only users can use**，属于“必须 user session”。citeturn29view0turn28view0  

下面逐项回答你列的能力清单，并按**已确认 / 待验证 / 不支持 / 高风险**标记（同时区分 Bot API / MTProto bot / MTProto user）。

## 频道日报的可行性

### 只用 Bot API，日报最稳妥能做到哪些字段

**已确认（可稳定）**  
- 频道基本信息（title/username 等）：`getChat`。citeturn13view0turn13view2  
- 订阅数（成员数）与净增长：`getChatMemberCount` 做每日/每窗口快照差分。citeturn13view1  
- 发帖数：统计窗口内收到的 `channel_post` 数量（前提：bot 接入后开始计）。citeturn25view0  
- 编辑数：统计 `edited_channel_post`。citeturn25view0turn10view1  
- 广告线索：窗口内从频道按钮进入 bot 的 `/start <payload>` 数量（见“来源归因”）。深链参数长度与字符集有明确限制。citeturn21view0  

**待验证（不建议作为日报核心，但可做增强）**  
- 反应（reactions）总量/增量：通过 `message_reaction_count` 更新做聚合（注意要求管理员 + allowed_updates，且有分钟级延迟）。citeturn25view0turn25view1  
- 新增/退订事件流：依赖 `chat_member` 更新是否覆盖频道订阅事件（需要实验）。citeturn25view0turn25view1  

> 关键现实：如果你要把“内容表现、曝光、互动”等做得像频道统计面板一样完整，**Bot API 单独不够**（至少在“稳妥/官方明确支持”的标准下，views/forwards 等缺失）。citeturn7view2turn9view1  

### 引入 MTProto 后，日报还能增加哪些字段

这里再细分为两档：

**MTProto（bot 身份）— 已确认可补齐“帖子级计数”**  
MTProto `message` 明确包含以下字段：  
- `views`：频道帖浏览量；  
- `forwards`：转发计数；  
- `reactions`：反应聚合结构；  
- `replies`：评论/回复信息（频道即“帖子评论”）。citeturn26view0  

配合 `channels.getMessages`（官方标注 bots 可用）即可按 message_id 拉取消息并更新这些计数快照。citeturn15search3  

据此，日报可增加（**已确认可实现，但工程量更高**）：  
- 窗口内发帖的 **累计浏览/平均浏览/Top N**  
- 窗口内发帖的 **累计转发/平均转发/Top N**  
- 窗口内发帖的 **累计 reactions / reactions 分布（按表情）**（仅聚合，不做用户列表）citeturn26view0turn25view0  
- 窗口内发帖的 **评论数/讨论热度**（用 `replies`）citeturn26view0  

**MTProto（user session）— 已确认可获得“官方统计图表与来源”但必须 user session**  
- `stats.getBroadcastStats`：followers、views_per_post、shares_per_post、growth_graph、views_by_source_graph 等丰富图表字段，但 **Only users can use**。citeturn29view0  
- 还要求频道达到某规模并且 `can_view_stats` 为 true，且要发往 `channelFull.stats_dc` 对应的数据中心。citeturn31view0  

### “每日浏览量”在 Telegram 场景的定义建议（客观、稳定、可计费）

先明确：MTProto 只说明 `views` 是“频道帖浏览量”，没有公开“去重规则/是否按用户去重”等更细定义，所以“计费口径”应以**可复现、可解释、可审计**为第一原则，而不是假装它等同于广告行业的严格 impression。citeturn26view0  

你要求比较的口径里，建议这样理解与取舍（以“可计费”为目标）：

- **口径 A：统计时间窗口内发布帖子的累计浏览总和**  
  - 做法：对窗口内发布的每条帖，取一个固定采样时点（例如窗口结束时）读 `message.views`，求和。citeturn26view0  
  - 问题：窗口末发布的帖子天然吃亏（曝光累积时间更短），会让日报波动与“发帖时刻”强相关。  
  - 结论：**待验证可用**（适合日报展示，不适合计费主口径）。

- **口径 B：时间窗口结束时最近 N 条帖子的累计浏览**  
  - 优点：对“频道当前热度”更直观。  
  - 问题：混入窗口外帖子，且 N 的选择会影响结果；不适合计费。  
  - 结论：**建议仅做“频道热度快照”展示**（待验证）。

- **口径 C：单帖平均浏览**  
  - 做法：窗口内帖子浏览总和 / 发帖数；  
  - 问题：小样本波动大；对“爆款”非常敏感。  
  - 结论：**适合做趋势指标**（建议有），不作为计费主口径。

- **口径 D：24 小时曝光**（强烈推荐作为一期可计费口径）  
  - 做法：每条帖发布后 **T+24h** 读取一次 `views` 并锁定为“24h views”。citeturn26view0  
  - 优点：跨天可比性好；对发布时间偏差更小；账单出具快。  
  - 风险：仍是累计 views 的一个截面；但可审计（两边复读同一时点）。  
  - 结论：**已确认可实现（需要 MTProto bot）**，**最适合第一版计费**。

- **口径 E：48 小时曝光 / 72 小时曝光**  
  - 优点：更接近“自然扩散完成后的曝光”；适合大频道。  
  - 代价：结算更慢；广告主体验“不到账”。  
  - 结论：**更适合二期提供多个套餐**（48h/72h）。

- **口径 F：生命周期总浏览**  
  - 问题：旧帖会持续长尾增长，账单永远不封账；容易产生纠纷。  
  - 结论：**不建议作为计费口径**（除非做“长尾分成/长期合约”，二期再谈）。

### 第一版产品最适合的日报字段方案

下面给出一个“**能上线、能坚持、能解释**”的日报字段（假设统计窗口支持“16:00—16:00”这类任意切窗，切窗本质是你侧调度与快照对齐）。

**必须有（一期 MVP 稳妥）**  
- 统计窗口（起止时间、时区）  
- 订阅数（窗口结束时）与净增长（与上个窗口快照差）citeturn13view1  
- 发帖数（窗口内）citeturn25view0  
- 广告线索数（从本频道按钮进入 bot 的 /start 归因数量）citeturn21view0  
- 频道“健康提醒”（规则化、可解释）：例如“今日未发帖 / 连续 N 天未发帖 / 最近 N 帖无互动”（不依赖平台隐藏数据）

**建议有（一期可做增强；视你是否启用 MTProto bot）**  
- 若仅 Bot API：编辑数（edited_channel_post）citeturn25view0turn10view1  
- 若启用 MTProto bot：  
  - 窗口内帖子 **Top 3（按 views）**、**Top 3（按 forwards）**、**Top 3（按 reactions）**citeturn26view0  
  - 窗口内帖子平均 views / forwards / reactions  
  - 窗口内评论数（replies）与“互动率”（reactions+comments / views）citeturn26view0  

**后期再加（依赖 user session 或复杂实验）**  
- 新增/退订拆分、增长来源（搜索/转发/邀请链接等）与官方图表：`stats.getBroadcastStats`（Only users）citeturn29view0turn31view0  
- 单帖小时级曲线/情绪图：`stats.getMessageStats`（Only users）citeturn28view0  

## 管理员触达与授权

### bot 能否主动私聊频道管理员发日报

**已确认的规则**：给用户发私聊消息，一般要求“用户先联系过 bot”。官方教程在“Sending Messages”明确写出：**The user must have contacted your bot first**（除“用户对有管理员 bot 的群发 join request”等少数例外）。citeturn14search6  

因此结论是：  
- **已确认**：若管理员在私聊里 `/start` 过 bot（或通过深链打开并触发 /start），bot 才能稳定每天私聊发日报。citeturn14search6turn21view0  
- **不支持（作为默认假设）**：对未启动 bot 的管理员“强行私聊推送日报”。  

### 是否必须管理员先启动 bot

- **已确认**：若日报要发到管理员私聊，必须管理员先启动。citeturn14search6  
- **已确认的替代路径**：把日报发送到一个“管理群/工作群”（bot 在群里），不要求每个管理员都启动 bot（但改变了交付形态）。  

### 多管理员场景的产品策略

**默认发给谁（一期建议）**  
- **建议默认目标**：以“首次完成绑定流程的管理员”为默认收件人（Owner）。  
- **可增强**：用 `getChatAdministrators` 找到 status=creator 的频道主作为推荐收件人（需要管理员也启动 bot 才能私聊）。citeturn13view1turn13view2  

**全部发送 / 订阅退订机制**

## 广告商入口与来源归因

### 从频道消息底部按钮进入 bot 时，如何识别用户来自哪个频道

**一期最简单且最稳妥的归因（已确认）**：用 **Deep Linking** 的 `start` 参数承载“频道来源 token”。  
- Telegram bots 的深链机制明确支持参数传递，允许字符集与长度上限（64）也写得很清楚，并建议用 base64url。citeturn21view0  
- 用户点击 URL 按钮打开 `https://t.me/<bot_username>?start=<token>` 后，你会收到 `/start <token>`。citeturn21view0  

**产品落地做法（已确认可执行）**  
- 为每个频道生成一个短 token（建议 8–16 字节随机 → base64url，保证 <=64 char）。citeturn21view0  
- 在频道每条贴追加按钮的 URL 固定为：`https://t.me/<bot>?start=<token>`。  
- 广告商进入 bot 后：  
  - 用 token 查到 `channel_id`（你库里有绑定关系），写入 advertiser_session 的 `ref_channel_id`；  
  - 后续广告商即使在 bot 内多次跳转，也默认沿用该 ref_channel_id，直到用户明确“切换频道/浏览更多频道”。

### deep link、Mini App、普通私聊菜单的优缺点

**Deep Link（推荐一期默认）— 已确认**  
- 优点：最短路径进入 bot；归因直接附在 /start 文本；参数长度/字符集可控。citeturn21view0  
- 缺点：UI 主要在 bot 私聊内；如果你想做更丰富的“频道介绍页/价格页/下单页”，可能需要再跳 Web/Mini App。

**Mini App（适合二期增强）— 已确认/待验证混合**  
- 已确认：Mini App 支持 `startapp` 参数，并会把 start_param 传给 Mini App；直链 Mini App 可感知 chat_type/chat_instance 作为“当前 chat 上下文”，但**直链 Mini App 本身不能读聊天内容**。citeturn21view1  
- 优点：更强的展示与下单体验（价格表、库存、合约条款、素材上传）。  
- 待验证点：是否能稳定从 Mini App 的上下文直接推出“频道 id”，以及在各种客户端/转发场景的丢失率。

**普通私聊菜单（不建议作为归因入口）— 不支持归因**  
- 如果用户只是从搜索打开 bot / 点击个人资料菜单进入，Bot API 更新里不会自动带“来源频道”。你只能把它当作“无来源自然流量”。

### 参数长度、兼容性、跳转损耗、归因丢失

- **已确认**：Deep link 参数 <=64 字符，且字符集限制明确。citeturn21view0  
- **待验证**：Mini App startapp 参数长度未在同一处给出硬上限（需要实验覆盖主流客户端）。citeturn21view1  
- **跳转损耗（产品经验）**：一步到位（Deep Link 进 bot）通常转化优于“先开 Mini App 再引导授权/再回 bot”；一期建议先跑通最短链路。

### 转发带按钮的消息，来源归因会不会出错

- **已确认的事实**：归因只取决于你按钮里的链接参数；消息被转发后，按钮 URL 通常仍保留。  
- **结论（产品定义问题）**：  
  - 这是“出错”还是“渠道外溢带来额外线索”，取决于你是否允许“二次传播仍归功原频道”。  
  - 一期建议：**默认仍归因原频道**（因为你无法从 /start 的 payload 判断用户是从哪个聊天界面点击的）。  

### 第一阶段最简单可用的归因设计（推荐）

**已确认可落地的最小设计**  
- 每个频道一个 `ref_token`（静态）。  
- 按钮 URL = `t.me/<bot>?start=<ref_token>`。citeturn21view0  
- bot 收到 `/start`：  
  - 若带 token：创建 advertiser_session（user_id, ref_channel_id, first_seen_at）；  
  - 后续所有“展示页/价格页/创建订单”默认绑定 ref_channel_id；  
  - 若无 token：进入“选择频道浏览”模式（二期再做推荐/市场）。  

## 广告计费与产品口径

你希望优先做“按展示/曝光扣费（CPM）”，不做 CPC。关键在于：**你是否拿得到一个可审计的“曝光计数”**。

### Telegram 频道场景里，“按曝光扣费”最合理的统计口径

- **已确认可用的最低层数据**：MTProto `message.views` 是“频道帖浏览量（View count for channel posts）”。citeturn26view0  
- **但需要你自己把它产品化**：views 是累计值，不自带“时间窗曝光”。因此“按曝光扣费”必须把口径设计成**锁定某个时点**或**计算两次快照差**，否则旧帖持续增长会导致账单永不封账。

**推荐作为计费基准的一期口径（已确认可实现，需要 MTProto bot）**  
- **24h views（锁定）**：广告帖发布后 T+24 小时读取一次 `views` 并锁定为“计费曝光”。citeturn26view0  
- 计费：`cost = ceil(views_24h / 1000) * CPM` 或 `cost = (views_24h / 1000) * CPM`（看你是否允许小数 Stars）。  
- 解释力：广告主与频道主都能在客户端看到同一条帖的 views（尽管 Telegram 未披露去重细则，但数值可复核）。

### 24h / 48h / 72h / 最终总浏览 的比较建议

- **24h**：结算快、体验好；对“发帖时间”偏差较小（因为每条帖都以发布时刻为起点）；适合一期。  
- **48h/72h**：更接近完整传播；适合二期作为“高级套餐”。  
- **最终总浏览**：不建议（账单不收敛、纠纷高）。  

### 置顶消息、重复曝光、旧帖持续增长的处理

- **置顶（Pinned）**：建议把“置顶”作为独立产品：  
  - 方案 1（一期推荐）：固定价（例如 24h 置顶 ¥X），并展示置顶期间 views 增量（需要快照差：views_end - views_start）。  
  - 方案 2（二期）：置顶按 CPM 结算，但“曝光窗口”固定为置顶时长，结束即封账。  
- **重复曝光**：Telegram 的 views 口径由平台决定（不披露去重）；产品上不要承诺“去重曝光”，只承诺“Telegram view counter”。citeturn26view0  
- **旧帖持续增长**：用“锁定时点”（24h/48h）或“活动期差分”封账即可。

### CPM 结算后台该怎么做

**一期可执行的结算对象**（基于锁定口径）  
- ad_post（某频道某条广告帖）  
- metric_snapshots：  
  - publish_at  
  - views_at_24h（锁定值）  
  - views_at_48h（可选）  
- billing：  
  - billable_impressions = views_at_24h  
  - amount = billable_impressions/1000 * cpm_price  
  - status = pending/charged/refunded  

### 第一阶段是否应先做“固定刊例价 + 数据展示”，而不是自动扣费

**推荐结论：是（一期优先固定刊例价），二期再自动扣费**  
原因是三类风险叠加：  
1) 计量体系尚处在“你自建口径”阶段（尤其如果一期不引入 MTProto bot，Bot API 侧无法稳定拿 views）。citeturn7view2turn26view0  
2) 自动扣费往往伴随“余额体系 + 支付合规”（见下一章 Stars 强约束）。citeturn22search0  
3) 纠纷处理与退款链路要提前做（Stars 下退款与对账也是产品工程）。citeturn22search0turn25view0  

### 计费模型建议（一期与二期）

**一期建议计费模型（稳妥）**  
- 固定刊例价：  
  - “单条广告帖（不置顶）¥X”  
  - “24h 置顶 ¥Y”  
- 报告展示：接入后提供该帖在 T+24h 看到的 views/forwards/reactions（若你做了 MTProto bot）。citeturn26view0  
- 收款：一期可先不在 bot 内完成交易（走人工合同/对公），避免踩 Stars 合规（见后文）。

**二期可升级模型**  
- CPM 自动结算（24h/48h lock）  
- 余额与预算控制（Stars 余额或 credits）  
- 广告上下架、续费提醒、投放频控等

**主要风险点**  
- views/forwards 为累计计数，口径争议要提前写入条款；  
- 若开始做自动扣费，支付体系必须与 Stars 合规对齐，否则移动端可能被限制展示。citeturn22search0  

## 支付与合规

### 是否必须使用 Telegram Stars

**已确认**：用于在 Telegram apps 内通过 bots/mini apps 销售数字商品和服务的支付，必须使用 Telegram Stars（currency `XTR`），并且“必须 exclusively use Telegram Stars”。citeturn22search0

**已确认：不可以（高风险）**

### 什么情况算“站内数字服务交易”，什么情况可以做站外支付

- **已确认的原则（Telegram 表述非常强）**：即使你在 Telegram 生态外有网站/其他支付渠道，只要你在 Telegram apps 内售卖数字商品与服务，仍必须使用 Stars。citeturn22search0  
- **推论（谨慎但很关键）**：若你在 bot 内完成“下单并交付数字服务（投放）”的闭环，却把支付引导到站外（USDT/卡），在规则上很可能被视为规避 Stars（高风险）。citeturn22search0

- **方案 A（最轻量）**：一期只做“渠道介绍页/价格页/线索收集”，不在 bot 内完成支付与自动扣费；成交走人工合同/对公（bot 只做 CRM）。这样避免触发 Stars 合规议题，同时能快速验证供需与定价。  
- **方案 B（更产品化但工程更重）**：一期直接走 Stars：  
  - 广告商在 bot 内购买“广告额度/投放套餐”（数字服务），支付用 Stars；citeturn22search0  
  - 后台把 Stars 交易映射成内部 credits，再做预算控制与扣减。  

## 推荐架构与 MVP 方案

### 纯 Bot API 方案能做到什么

**已确认可交付的能力**  
- 频道接入与绑定：`getChat` / `getChatMemberCount` / `getChatAdministrators`；并可用 `KeyboardButtonRequestChat(chat_is_channel=true)` 做“选择频道→授权”体验。citeturn13view1turn24view0turn23view0  
- 新帖与编辑事件采集：`channel_post` / `edited_channel_post`。citeturn25view0turn10view1  
- 频道贴自动追加“广告投放入口”按钮：`editMessageReplyMarkup`，并注意“只能编辑无 reply_markup 或带 inline keyboard 的消息”。citeturn12view3turn12view0  
- 日报（基础版）：订阅数快照、净增长、发帖数、编辑数、广告线索数。citeturn13view1turn25view0turn21view0  
- Reaction（可能）：若你开启 allowed_updates 并满足管理员要求，可收 `message_reaction_count` 聚合更新，但存在延迟（分钟级）。citeturn25view0turn25view1  

**做不到或不稳妥的关键点**  
- “浏览量/转发量”在 Bot API 文档中没有字段定义，按“稳妥”标准视为不可依赖（除非你愿意把它放在“待验证/非核心”）。citeturn7view2turn9view1  
- “官方频道统计面板同款数据”（增长来源、图表）Bot API 不提供。citeturn29view0  

### Bot API + MTProto（bot）混合方案能做到什么

这是我认为**最适合你这个方向的“二期主线”，也可能是你“一期想做曝光计费”时的最低成本路径**：不碰 user session，但补齐关键计数。

**已确认可补齐的核心能力**  
- 帖子级 views/forwards/reactions/replies：MTProto `message` 字段明确存在。citeturn26view0  
- `channels.getMessages` 标注 bot 可用，用于按 message_id 拉取消息并刷新计数快照。citeturn15search3  

**因此可新增产品能力**  
- “内容表现”日报：Top 帖（views/forwards/reactions）、均值、互动率。  
- “按曝光计费”的基础：24h/48h views 锁定、置顶期间 views 差分。  
- 历史贴回填（待验证）：若你实现 MTProto 的分页历史拉取，可对接入前 N 天贴补齐数据与按钮（工程量较大，建议二期）。

### 第一阶段 MVP 建议做哪些功能

以“最小可行 + 最大验证价值”为原则（并兼顾合规），建议一期把功能压成 3 条主线：

**主线一：频道管理员侧（必做）**  
- 绑定频道（RequestChat 选择频道 + 授权）citeturn24view0turn23view0  
- 日报（基础版）：订阅数快照/净增长、发帖数、编辑数、广告线索数citeturn13view1turn25view0turn21view0  
- 自动追加“投放广告”按钮（只改 reply_markup）citeturn12view3turn12view0  
- 广告位配置（刊例价、置顶/非置顶、投放规则、预算提醒、收益统计）——这些是你自建数据，不依赖平台灰区

**主线二：广告商侧（必做）**  
- 从频道按钮 deep link 进入 bot，识别来源频道 token，展示该频道“投放介绍页/价格页/联系方式/下单意向”。citeturn21view0  
- 创建“意向订单/询单”（不一定一期就自动扣费）

**主线三：合规与支付（一期建议轻量）**  
- 一期不在 Telegram 内完成数字服务支付（走线索→人工成交），先验证供需与定价；或若你必须站内闭环，则直接 Stars。citeturn22search0  

### 哪些功能必须延后

- “官方统计面板同款数据”（增长来源、图形曲线）：必须 user session（Only users），建议二期且默认不启用。citeturn29view0turn31view0  
- 自动扣费 CPM：如果你一期不做 MTProto bot，则缺少稳妥 views；若你做 MTProto bot，则仍建议先跑“锁定口径 + 手动结算”一段时间再自动化。citeturn26view0  
- 邀请链接归因新增订阅：Bot API 的 `chat_member`/`invite_link` 机制需要在频道场景验证覆盖率与吞吐。citeturn13view2turn25view0  

### 最容易踩 Telegram 规则或技术边界的地方

- **支付**：数字服务在 Telegram apps 内必须 Stars；引导 crypto/第三方支付属于高风险，可能导致移动端不可展示。citeturn22search0  
- **去匿名化**：频道帖 reactions 不能获取用户列表（反去匿名限制）。citeturn15search1  
- **依赖 user session 的统计**：`stats.getBroadcastStats`/`stats.getMessageStats` Only users，意味着你要处理账号登录态与安全责任（并可能引发平台风控）。citeturn29view0turn28view0  
- **更新丢失**：Bot API 更新最多保留 24h；你的 webhook/worker 必须稳定。citeturn25view0
